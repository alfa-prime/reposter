# Фоновые задачи: поэтапный переход на Celery

Состояние задачи и бизнес-данные хранятся в PostgreSQL. В профиле `background`
рерайт, сбор и обслуживание доставляются через Celery и Redis; публикация пока
исполняется прежним PostgreSQL воркером. По умолчанию
`BACKGROUND_TASKS_ENABLED=false`, `BACKGROUND_TASK_TRANSPORT=postgres`.
`compose.tasks.yaml` включает Redis, диспетчер outbox и четыре типа исполнителей.
Планировщики сбора, публикации и очистки работают в отдельном сервисе `scheduler`
из `compose.yaml`. FastAPI не запускает планировщики в своём процессе.
Кнопки рерайта и ручного сбора используют асинхронные endpoints, когда фоновые
задачи включены. Пока `BACKGROUND_TASKS_ENABLED=false`, работают прежние
синхронные endpoints; публикация в интерфейсе пока работает по старому сценарию.

## Состояния и гарантии

`pending → running → succeeded | retry_wait | failed | needs_review`.
Из `retry_wait` задача снова переходит в `running`. Ожидающую задачу можно отменить
(`cancelled`), выполняющуюся — нельзя: внешнее действие уже могло начаться.

- `enqueue()` не делает commit. Намерение, бизнес-изменение и outbox сохраняются
  одной транзакцией вызывающего кода. Откат удаляет все три изменения.
- Уникальный ключ идемпотентности возвращает прежнюю задачу. Повтор ключа с другим
  payload отклоняется. Для одного материала в одной очереди разрешена одна активная
  задача; для сбора и обслуживания используются глобальные subject `0`.
- Диспетчер отправляет только сохранённый ID и имя очереди. Доставка at-least-once:
  сбой после принятия сообщения может дать повтор. PostgreSQL transport сохраняет
  уникальную квитанцию `task_deliveries`; Celery доставляет точный ID задачи, который
  захватывается в базе только если задача готова к исполнению. Повтор не создаёт
  вторую задачу. Диспетчер заново отправляет готовые `retry_wait` и застрявшие
  более двух минут `pending` рерайты, сборы и обслуживание: это также восстанавливает потерянные Redis
  сообщения. Дубликаты допустимы, их отсекает захват строки PostgreSQL.
- Исполнитель захватывает строку через `FOR UPDATE SKIP LOCKED`, создаёт случайный
  token и lease на 90 секунд. Продление — каждые 30 секунд. Завершение проверяет
  token и срок lease. Старый исполнитель не может записать результат после потери
  владения. Блокировки задачи не удерживаются во время внешних запросов.
- Рерайт сравнивает снимок текста, промпта и версии материала до запроса и при записи.
  Изменения редактора сохраняются. Права и доступ к каналу перепроверяются при исполнении
  и перед сохранением рерайта; удалённый пользователь не становится системным actor.
- Перед отправкой в MAX сохраняется `sending` и связь попытки с задачей. Подтверждение
  публикации и `succeeded` сохраняются атомарно. Обрыв после резервирования отправки,
  потеря ответа или таймаут приводят к `needs_review` и `publication_unknown`.
  Автоматического повторного отправления при неизвестном результате нет. Проверка
  канала и подтверждение/повтор выполняются через существующий сценарий восстановления.
  Если lease истёк до сохранения `sending`, отправка не начиналась и повтор безопасен.
- Сбор использует существующую advisory lock, дедупликацию постов и checkpoints.
  Частичные ошибки источников возвращаются в результате `partial`, записываются в
  журнал и проверяются в следующем сборе. Восстановление закрывает только историю
  запуска, связанного с истёкшей задачей.

Payload содержит рабочий снимок материала, но не токены интеграций. API состояния
не возвращает payload или lease token. Тексты не следует публиковать в логах.

## Очереди и повторы

| Очередь | Попытки всего | Таймаут попытки | Задержка первого повтора | Предел backoff |
|---|---:|---:|---:|---:|
| rewrite | 3 | 180 с | 7,5–15 с | 300 с |
| collection | 3 | 1800 с | 15–30 с | 600 с |
| publication | 3 | 600 с | 7,5–15 с | 300 с |
| maintenance | 2 | 900 с | 30–60 с | 600 с |

Backoff экспоненциальный с jitter. Числовой `Retry-After` — нижняя граница ожидания.
Сетевые ошибки и HTTP 429/5xx повторяются для безопасных операций. Ошибки конфигурации,
прав, изменённого материала, HTTP 4xx и неожиданные ошибки заканчиваются `failed`.
Публикация повторяется только после однозначного отказа (429) или временного сбоя
загрузки медиа до отправки сообщения; неопределённый результат требует проверки.
Бюджет повторов внешней операции независим от outbox: транспорт повторяет доставку
неограниченно с задержкой до 300 секунд, не расходуя попытки выполнения задачи.

## API

Авторизация, текущие права, доступ к каналу, CSRF и same-origin обязательны.

- `POST /api/v1/queue/{id}/rewrite-task`
- `POST /api/v1/queue/{id}/publish-task`
- `POST /api/v1/system/collection/tasks`

Тело: `{"idempotency_key":"unique-operation-key"}` (8–128 ASCII символов).
Ответ `202` содержит `task_id`. Повтор того же HTTP запроса возвращает прежний ID,
даже если материал уже изменился после его принятия. Новая операция требует нового ключа.
`GET /api/v1/tasks/{task_id}` возвращает состояние, счётчик попыток, безопасный код
ошибки и результат. `POST /api/v1/tasks/{task_id}/cancel` отменяет ожидание;
пользователь может отменять свои задачи, администратор — также системные.

Интерфейс хранит ID задачи и ключ идемпотентности в рамках вкладки браузера:
после обновления страницы можно открыть материал и продолжить отслеживание.
Если ответ на постановку в очередь потерялся, повторный клик использует тот же ключ.
Проверка состояния прекращается при закрытии карточки; сама задача продолжает
выполняться на сервере. Статус ошибки показывается в интерфейсе.

Плановые публикации имеют ключ из ID и снимка материала, включающего `scheduled_at`.
Один слот расписания ставится в очередь один раз, включая отменённые/ошибочные задачи.
Для нового запуска после окончательной ошибки следует заново назначить время публикации.
Сбор дедуплицируется по интервалу расписания; обслуживание — по дате UTC.

## Включение на сервере

Сначала резервная копия и проверка восстановления (`backup/run-backup.sh`,
`backup/run-verify.sh`). Применение миграции `0020_background_tasks` добавляет таблицы
и nullable связи, существующие данные не переписываются. DDL ограничен lock timeout
2 секунды и statement timeout 30 секунд. При занятой схеме миграция завершается
ошибкой, а не удерживает длительную блокировку.

Профиль `background` теперь поднимает Redis с AOF и политикой `noeviction`.
Пример последовательности после резервной копии и проверки миграций:

```sh
docker compose -f compose.yaml -f compose.prod.yaml -f compose.tasks.yaml --profile background build app scheduler migrate task-outbox task-rewrite task-collection task-maintenance
docker compose -f compose.yaml -f compose.prod.yaml -f compose.tasks.yaml --profile background up -d --no-build app scheduler redis task-outbox task-rewrite task-collection task-publication task-maintenance
```

Воркеры используют один образ приложения, общий media volume и доверенные TLS
сертификаты. На контейнер установлен предел 512 МБ и 0,5 CPU; Celery рерайт
использует два дочерних процесса. Пул БД фоновых контейнеров ограничен 2+2
соединениями на процесс. Перед масштабированием
нужно проверить общий бюджет подключений PostgreSQL и памяти. После включения всегда
использовать все три compose файла и профиль `background` при управлении приложением.
Отдельный `scheduler` также работает при обычном запуске двух compose файлов и
выполняет прежние задачи напрямую, когда фоновые задачи отключены. При
редактировании расписания API сохраняет настройки в PostgreSQL, планировщик
перечитывает их в течение 10 секунд. Лидерство защищено сеансовой блокировкой
PostgreSQL: вторая копия ждёт освобождения блокировки. При потере соединения
планировщик останавливает циклы и заново получает лидерство.

Проверить `/health`, состояния контейнеров, логи scheduler/dispatcher/worker, новые запуски сбора
и отсутствие рестартов. Для наблюдения (в read-only транзакции):

```sql
SELECT queue, state, count(*), min(created_at) AS oldest
FROM background_tasks GROUP BY queue, state ORDER BY queue, state;
SELECT count(*) AS undelivered, min(created_at) AS oldest
FROM background_tasks WHERE task_id IN
  (SELECT task_id FROM task_outbox WHERE delivered_at IS NULL);
SELECT task_id, queue, error_code, attempts
FROM background_tasks WHERE state IN ('failed', 'needs_review')
ORDER BY finished_at DESC LIMIT 20;
```

Не удалять task/outbox записи автоматически: они обеспечивают дедупликацию.
Политику архивирования и срок хранения ключей нужно определить отдельно.

## Откат исполнения

1. Остановить `scheduler` в профиле `background` и пересоздать app с обычными
   compose файлами и `BACKGROUND_TASKS_ENABLED=false` в `.env`.
   Дождаться завершения `running` задач; при аварийном останове публикация
   требует проверки канала.
2. Остановить `task-outbox` и четыре task worker. При аварийном останове
   `python -m news_reposter.background.worker --recover` закрывает просроченные
   lease; новые задачи в этот момент не принимать. Сначала проверить все
   `sending`/`publication_unknown`. Затем запустить `scheduler` с обычными
   compose файлами и `BACKGROUND_TASKS_ENABLED=false`.
3. При необходимости вернуть предыдущий образ приложения. Таблицы задач оставлять:
   это история и ключи дедупликации. Production downgrade миграции удалит историю
   и для обычного отката не нужен.

## Следующие этапы

Планировщики вынесены из FastAPI в отдельный процесс. Перед завершением перехода
и запуском нескольких процессов API нужно перенести публикацию на Celery с
сохранением проверки неопределённой отправки:
повторная доставка сообщения из брокера не гарантирует единственной отправки в MAX.
