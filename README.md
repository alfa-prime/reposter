# News Reposter

Сервис автоматически собирает новые публикации из VK, складывает их в
редакционную очередь и после модерации публикует в подключённые каналы MAX.
Прямой маршрут VK → MAX отключён: каждая публикация проходит через очередь и
сохраняется в истории.

## Что уже работает

- несколько VK-источников и несколько целевых каналов MAX;
- привязка источников к конкретным каналам;
- автоматический сбор по настраиваемому расписанию и ручной запуск из админки;
- журнал запусков с результатом по каждому источнику;
- загрузка всех записей, появившихся после последней сохранённой, включая
  объём больше одной страницы VK;
- редакционная очередь: текст, подпись, фотографии, видео, модерация и архив;
- немедленная и запланированная публикация в MAX;
- защита от одновременной повторной отправки одного поста;
- GigaChat-рерайт как необязательный инструмент редактора;
- пользовательский вход с серверными сессиями, ролями и разрешениями;
- назначение редакторам одного или нескольких доступных каналов;
- ограничение очереди, карточек и действий только назначенными каналами;
- отдельные журналы планировщика, пользователей и редакционных действий;
- переход из редакционного журнала прямо к конкретному материалу;
- самостоятельная загрузка пользовательских аватаров;
- зашифрованные резервные копии PostgreSQL и медиа в S3;
- контроль восстановления, диска, контейнеров и базы с уведомлениями ntfy;
- атомарная запись редакционных изменений вместе с журналом аудита;
- управляемый пул соединений PostgreSQL и межпроцессная блокировка сборщика;
- PostgreSQL, Alembic, Docker Compose и web-интерфейс на React.

## Как работает сбор

При первом успешном обращении к новому источнику сервис сохраняет только его
последнюю незакреплённую запись. Это создаёт точку отсчёта и не заполняет
очередь всей историей сообщества.

При каждом следующем проходе сервис находит последний сохранённый ID и
загружает **все** более новые записи в хронологическом порядке. Если появилось
10, 150 или больше постов, клиент VK проходит нужное число страниц и не
ограничивается первыми 100 результатами.

После первой установки автоматический сбор отключён. В разделе «Планировщик»
задаются рабочий период, интервал и часовой пояс. Период
может переходить через полночь, например 20:00–08:00. Изменения начинают
действовать сразу, перезапуск контейнеров не нужен.

Ручная кнопка и планировщик используют один и тот же сборщик. Локальная и
PostgreSQL-блокировки не позволяют выполнять проход одновременно даже в разных
процессах приложения. Результаты сохраняются в «Журналы → Журнал
планировщика»: там видны найденные публикации, созданные элементы очереди,
ошибки и точки продолжения по каждому источнику.

## Пользователи, каналы и журналы

Администратор назначает обычному пользователю один или несколько каналов.
Новый пользователь по умолчанию не имеет назначенных каналов. В очереди он
видит материал, если ему доступен хотя бы один его канал; в карточке остаются
только доступные назначения, и действия выполняются только над ними.
Недоступные назначения нельзя изменить или удалить.

Администратор всегда имеет глобальный доступ ко всем каналам, поэтому выбор
каналов для его собственной учётной записи не показывается. Удаление канала
автоматически удаляет связанные назначения пользователей.

В меню «Журналы» доступны:

- журнал планировщика — сбор источников и ошибки по каждому запуску;
- журнал пользователей — административные изменения учётных записей и доступа;
- редакционный журнал — создание, редактирование, рерайт, модерация,
  планирование, публикация и удаление материалов.

Редакционная запись содержит сотрудника, канал, действие, время и ID материала.
По ID можно открыть соответствующую карточку очереди.

## Надёжность и восстановление

Изменение материала и запись редакционного аудита сохраняются одной транзакцией:
если одна часть не записалась, откатывается вся операция. Сборщик защищён от
одновременного запуска внутри одного процесса и между разными процессами через
PostgreSQL advisory-lock.

Рабочая конфигурация поддерживает зашифрованные Restic-копии базы и медиа в
S3. По умолчанию хранятся 14 ежедневных, 8 еженедельных и 6 ежемесячных снимков.
Отдельная задача регулярно проверяет целостность репозитория. Мониторинг ntfy
каждые пять минут проверяет сайт, базу, контейнеры, диск и свежесть последней
копии. Подробная установка и восстановление описаны в [DEPLOY.md](DEPLOY.md).

## Быстрый запуск в Docker

```bash
cp .env.example .env
docker compose up -d --build
docker compose ps
```

Админка будет доступна на порту, заданном через `HTTP_PORT` (по умолчанию 80),
API — внутри проекта на порту 8000. Перед стартом приложения контейнер
`migrate` ожидает PostgreSQL и применяет миграции Alembic.

Полезные команды:

```bash
docker compose logs -f app
docker compose down
docker compose -f compose.yaml up -d --build
```

Последняя команда запускает базовую конфигурацию без development override.

## Основные настройки

Минимальный `.env`:

```dotenv
VK_ACCESS_TOKEN=сервисный_ключ_VK
VK_API_VERSION=5.199

MAX_ACCESS_TOKEN=токен_бота_MAX
MAX_API_URL=https://platform-api2.max.ru

POSTGRES_DB=news_reposter
POSTGRES_USER=news_reposter
POSTGRES_PASSWORD=news_reposter
POSTGRES_HOST=postgres
POSTGRES_PORT=5432
DATABASE_POOL_SIZE=10
DATABASE_MAX_OVERFLOW=10
DATABASE_POOL_TIMEOUT_SECONDS=30
DATABASE_POOL_RECYCLE_SECONDS=1800
DATABASE_COMMAND_TIMEOUT_SECONDS=30
```

Расписание намеренно не хранится в `.env`: после запуска оно настраивается в
интерфейсе и сохраняется в PostgreSQL. Начальное значение — «отключено»;
предзаполнены интервал 15 минут, период 08:00–20:00 и `Europe/Moscow`.

## Логи и диагностика

Приложение пишет логи в `stdout` в едином UTC-формате. Уровень задаётся через
`LOG_LEVEL` (`INFO` по умолчанию). Каждый HTTP-запрос получает `request_id`,
который возвращается в заголовке `X-Request-ID` и добавляется ко всем
прикладным логам этого запроса. Неожиданные ошибки возвращают безопасный ответ
`500` с тем же `request_id`, а полный traceback остаётся только в журнале.

Docker хранит не более пяти файлов логов по 10 МБ для каждого контейнера.
Посмотреть последние записи приложения:

```bash
docker compose -f compose.yaml -f compose.prod.yaml logs --tail=100 app
```

## Подключение MAX

Канал добавляется в интерфейсе по публичной ссылке. Чтобы приложение узнало
его `chat_id`:

1. задайте `MAX_WEBHOOK_URL` и `MAX_WEBHOOK_SECRET`;
2. под учётной записью с разрешением `targets.manage` создайте подписку через
   `POST /api/v1/max/subscriptions/channel-discovery`;
3. добавьте бота в канал и назначьте администратором;
4. после webhook-события добавьте канал в разделе «Целевые каналы».

API MAX может требовать сертификаты Минцифры. Если они не установлены в
системное хранилище, положите объединённый PEM в `certs/` и задайте:

```dotenv
HTTP_CA_FILE=/app/certs/russian_trusted_ca.pem
```

Файлы `certs/*.pem` не попадают в Git и Docker build context.

## GigaChat

Рерайт необязателен. Для него задаются `GIGACHAT_CREDENTIALS`,
`GIGACHAT_SCOPE` и `GIGACHAT_MODEL`. Дополнительные доверенные сертификаты
задаются для общего HTTP-клиента через `HTTP_CA_FILE`.
Без credentials сбор, редактирование, модерация и публикация продолжают
работать; недоступна только генерация текста.

## Пользовательские сессии

Backend поддерживает непрозрачные серверные сессии. При успешном
`POST /api/v1/auth/login` браузер получает две cookie: HttpOnly-cookie сессии и
отдельную cookie CSRF. В PostgreSQL хранятся только SHA-256-отпечатки токенов.
Сессия ограничена idle-таймаутом и абсолютным сроком жизни, может быть отозвана
на сервере, а роли и разрешения перечитываются из базы при каждом запросе.

В production cookie имеют префикс `__Host-`, флаги `Secure`, `SameSite=Strict`
и `Path=/` без `Domain`. Поэтому `AUTH_COOKIE_SECURE=true` следует менять на
`false` только при локальной разработке по обычному HTTP.

Доступны маршруты:

- `POST /api/v1/auth/login` — вход по логину и паролю;
- `GET /api/v1/auth/me` — текущий профиль, роли и разрешения;
- `POST /api/v1/auth/change-password` — смена пароля с отзывом прежних сессий;
- `POST /api/v1/auth/logout` — завершение текущей сессии;
- `POST /api/v1/auth/logout-all` — завершение всех сессий пользователя.

Изменяющие запросы, защищённые пользовательской сессией, дополнительно требуют
CSRF-токен из cookie в заголовке `X-CSRF-Token` и проверку источника запроса.
Токены никогда не возвращаются в JSON.

При смене пароля backend проверяет текущий пароль, применяет общую политику
длины к новому паролю, сбрасывает `must_change_password`, отзывает все прежние
сессии с причиной `password_changed` и выдаёт браузеру одну новую пару cookie.
Смена хеша, отзыв и создание сессии выполняются одной транзакцией.

Frontend при открытии проверяет `/api/v1/auth/me`, показывает форму входа при
отсутствующей или истёкшей сессии и не загружает редакционные данные до
успешной аутентификации. В боковой панели доступны текущий пользователь,
его роли, обычный выход и завершение всех своих сессий.
Пользователь может самостоятельно загрузить или удалить свой аватар; файлы
JPEG, PNG и WebP размером до 5 МБ хранятся в постоянном `media_data` volume.

Если профиль содержит `must_change_password=true`, frontend не монтирует
редакционный интерфейс и показывает обязательную форму смены временного
пароля. После успешной замены новая сессия сразу открывает приложение;
пользователь также может выйти и войти под другой учётной записью.

Прикладные маршруты используют пользовательские разрешения. Чтение настроек,
состояния и истории планировщика требует
действующую сессию и разрешение `scheduler.read`; чтение очереди, карточек и
медиа — сессию и разрешение `queue.read`; просмотр источников и каналов —
разрешения `sources.read` и `targets.read`; управление ими — `sources.manage`
и `targets.manage`. Изменение очереди разделено на разрешения `queue.edit`,
`queue.rewrite`, `queue.submit`, `queue.moderate`, `queue.schedule` и
`queue.publish`. Все изменяющие операции с пользовательской сессией требуют
CSRF-токен и проверку источника запроса. Ручной сбор требует `collection.run`,
а изменение расписания — `scheduler.manage`. Вспомогательные операции VK
проверяют `sources.read` или `sources.manage`, операции настройки MAX —
`targets.manage`, а тест LLM — `queue.rewrite`. Caddy отвечает только за HTTPS,
раздачу frontend и проксирование запросов; отдельный Basic Auth больше не
используется.

## API и ручной сбор

Маршрут входа публичен. Проверка сессии `/api/v1/auth/me`, выход, чтение данных
планировщика, очереди и справочников, а также управление очередью, источниками,
каналами и сбором защищены пользовательской сессией; webhook MAX — собственным
секретом. Health-check маршруты публичны.

```bash
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/health/database
```

Запустить тот же проход сборщика вне расписания:

```bash
curl -X POST \
  -b '__Host-rp_session=токен_сессии; __Host-rp_csrf=csrf_токен' \
  -H 'X-CSRF-Token: csrf_токен' \
  http://127.0.0.1:8000/api/v1/system/collect-now
```

У пользователя должно быть разрешение `collection.run`.

Интерактивная документация: <http://127.0.0.1:8000/docs>.

## Хранение данных

- `posts` — исходные публикации VK с уникальной парой
  `source_id + external_post_id`;
- `post_attachments` — фотографии и видео исходного поста;
- `queue_items` — отдельная редакционная версия для каждого целевого канала;
- `publications` — технический статус, число попыток и результат отправки;
- `data/media` — загруженные редактором фото, видео и порядок медиа.

Удаление элемента очереди, источника или канала также очищает связанные файлы
из `data/media`.
